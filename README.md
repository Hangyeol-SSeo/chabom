# 차봄 · Chabom

**내 차를 고르는 공간.** 관심 있는 중고차를 한 번 더 살펴보고, 차량과 딜러를 보관하는 개인용 서비스입니다.

프로젝트 폴더와 Git 저장소 루트는 `chabom/`입니다. 상위 `NemoNemo/`는 저장소에 포함하지 않습니다.

`used-car-selector-spec.md` 명세에서 출발했지만, 두 차례의 아키텍처 개편을 거쳐 지금은
**여러 매물을 훑어보는 검색 도구가 아니라, 이미 찾은 매물 1건을 깊게 검증하는 도구**다. 사용
언어/도구: **Python 3.13**, `Playwright`(단발성 실브라우저 조회) + `BeautifulSoup4`(HTML 파싱),
`FastAPI`+`uvicorn`(로컬 검증 서버), `PyYAML`(가중치 설정), `sqlite3`(딜러 블랙리스트·이력
저장), `pytest`(단위 테스트).

> **2026-09-18 두 번째 아키텍처 개편 — 점수 기반 마켓플레이스에서 체크리스트 검증 도구로.**
> 사용자가 실시간 검색 웹앱(첫 번째 개편의 결과물)에 다섯 가지 문제를 제기했다: (1) robots.txt/
> 봇 차단으로 일괄 크롤링이 원천적으로 불안정, (2) 0~100 합산 점수에 의존하게 되어 핵심 결함이
> 있어도 "65점"처럼 그럴듯해 보임, (3) 성능기록부·보험이력처럼 가장 중요한 정보를 크롤링으로
> 확보 못함, (4) 필터가 부족해 원치 않는 차종까지 섞여 나옴(예: 모닝·캐스퍼만 보고 싶은데
> 포터도 나옴), (5) 나쁜 매물을 반복해서 올리는 딜러를 걸러낼 방법이 없음. 그리고 원칙을
> 하나 제시했다: **"2종 오류(정상 차량을 부실로 오판)는 감수할 수 있지만, 1종 오류(부실
> 차량을 정상으로 오판)는 절대 안 된다 — 차는 한 번만 잘 사면 된다."**
>
> 그래서 지금은 사용자가 각 사이트의 뛰어난 자체 검색으로 후보를 직접 찾고(문제 4 해결 —
> 필터를 재구현하지 않는다), 매물 링크 하나를 이 서버에 주면(또는 직접 입력하면) 그 한 건만
> 열어서 검증한다(문제 1 해결 — 대량 크롤링이 아니라 사람이 링크 하나를 클릭하는 것과 동일한
> 단발성 조회). 판정은 0~100 점수가 아니라 항목별 PASS/FAIL/미확인 **체크리스트**이며,
> 성능기록부·보험이력처럼 크롤링으로 못 가져오는 항목은 **사용자가 직접 확인해서 입력하지
> 않으면 자동으로 "미확인"으로 게이팅되어 전체 판정이 "보류"로 강제된다**(문제 2, 3 해결 —
> `scoring/checklist.py` 참고). 딜러는 sqlite에 누적 저장되어, 한 번 "제외" 등록하면 이후 같은
> 딜러의 다른 매물을 검증할 때 자동으로 걸린다 — 이름이 아니라 사이트별 판매자 ID로
> 식별한다(문제 5 해결 — `storage/dealers.py` 참고).
>
> 이전의 실시간 검색 마켓플레이스(가격/연식/필터로 여러 매물을 긁어와 카드로 보여주던 버전)는
> 완전히 대체됐다 — `server.py`/`web/index.html`이 이 커밋에서 통째로 새 버전으로 바뀌었다.
> 그 이전의 "전량 크롤링 후 정적 Artifact 발행" 버전에 대한 이력은 git 로그(또는 이 문서의
> 이전 리비전)에 남아 있다.

> **2026-09-20 정정 — 케이카 단건 조회 지원 추가(단, robots.txt 판단이 아니라 별도의 의식적
> 예외다).** "케이카·엔카는 robots.txt로 상세페이지가 막혀 있어 자동으로 못 연다"고
> 일괄적으로 설명했었는데, 사용자가 정확히 지적했다: 링크 1건을 여는 건 크롤링이 아니라
> 사람이 그 링크를 클릭하는 것과 같은데 왜 막느냐는 것. **케이카 상세페이지(`/bc/detail/
> carInfoDtl?`)는 실제로 지금도 robots.txt에 Disallow로 명시되어 있다** — 이건 보배드림·
> KB차차차 때처럼 "알고 보니 안 막혀 있었다"는 오판 정정이 아니다. 대신 이 프로젝트는
> "자동화된 크롤러의 반복 수집을 막는 규약"과 "사용자가 직접 준 링크 1건을 여는 단발 조회"를
> 서로 다른 것으로 취급하기로 판단을 바꿨다 — 후자는 이미 `verification_links`로 사용자에게
> "이 링크를 직접 클릭해서 확인하라"고 안내해오던 것과 실질적으로 같고(사람이 클릭 vs.
> 사용자 요청으로 도구가 대신 클릭), 이번엔 그 클릭을 도구가 대신 해줄 뿐이다. 이건 규제를
> "안 지키기"로 한 게 아니라 애초에 이 상황이 규제가 겨냥한 대상이 아니라고 재해석한
> 것이며, 사용자가 이 재해석에 동의해 진행을 요청했다. 실제로 열어보니 케이카 상세페이지는
> **차량평가사가 직접 진단한 외판/프레임 손상 여부를 따로 보여준다** — 보배드림·KB차차차
> 프레임 손상을 실제로 자동 판정할 수 있는 신호였다. 그래서
> 케이카는 이제 `/api/lookup`을 지원하며(`crawler/adapters/kcar_detail_adapter.py`), 이
> 소스에서는 ①번 프레임 손상 항목이 대부분 자동으로 채워진다.
>
> **2026-09-20 추가 — 엔카 단건 조회 지원 추가.** 사용자가 "엔카가 제일 중요하다"며 실제
> 매물 링크를 직접 줘서 조사했다. 실제 상세 URL은 `fem.encar.com/cars/detail/{id}`이고,
> 이 경로도 케이카와 마찬가지로 robots.txt에 지금도 `Disallow: /cars/detail/`로 명시되어
> 있다 — 같은 의식적 예외 판단을 그대로 적용했다. 페이지가 렌더링되며 브라우저가 자동으로
> `api.encar.com/v1/readside/...`를 호출해 보험이력을 채우는데, 이 호스트는 robots.txt가
> `Disallow: /`(전체 차단)라서 **그 API는 절대 직접 호출하지 않는다** — Playwright가 페이지를
> 열 때 자연히 발생하는 부수 요청만 허용하고, 최종 렌더링된 결과만 읽는다(사람이 그 링크를
> 직접 열어도 똑같이 발생하는 요청이다). 엔카 상세페이지에는 `window.__PRELOADED_STATE__`라는
> 구조화 JSON이 있어 제조사·모델·가격·주행거리·연료·변속기·신차가격·딜러 연락처까지 안정적으로
> 읽을 수 있었다(`crawler/adapters/encar_detail_adapter.py`). 2026-10-01부터는 성능기록부
> 창과 로그인된 차량 상세 이력 화면도 읽는다. 로그인되지 않은 차봄 브라우저에서는 보험 상세를
> 미확인으로 유지하고 원문 링크를 제공한다(아래 "엔카 단건 조회" 절 참고).

## 사용법 요약

1. 원하는 사이트(보배드림·KB차차차·케이카·엔카 등 아무 곳이나)에서 평소처럼 검색해 마음에 드는
   매물을 찾는다 — 이 프로그램은 검색을 대신해주지 않는다.
2. 이 프로그램(`python server.py` → `localhost:8000`)에 그 매물 링크를 붙여넣거나 직접 입력한다.
3. **보험 상세·성능기록부**가 자동으로 확보된 항목은 결과에 표시된다. 엔카 보험 상세는
   차봄의 **매물 확인 → 엔카 보험 상세 연결**에서 로그인 창을 열고 직접 로그인한 뒤
   **로그인 완료 확인**을 누르면 이후 조회에 자동 반영된다. 미확인
   항목은 원문에서 확인한 뒤 직접 답한다. 답하지 않으면 전체 판정이 보류된다.
4. "검증하기"를 누르면 항목별 PASS/FAIL/미확인과 종합 판정(통과/보류)이 나온다.
5. 결격 사유를 발견했고 그게 딜러의 문제라고 판단되면 "이 딜러 제외 등록"을 눌러둔다 — 다음에
   같은 딜러의 다른 매물을 검증할 때 자동으로 보류 처리된다.

**KB차차차 봇 차단 관련(중요)**: 짧은 기간에 여러 링크를 연속 조회하면 "로봇여부 확인" 봇 차단
페이지가 돌아올 수 있다. 이 프로그램은 그런 응답을 감지해 조회 실패로 처리할 뿐(`crawler/
adapters/kbchachacha_adapter.py::_looks_like_bot_block`) **우회는 절대 하지 않는다** —
User-Agent 위장, 자동화 감지 회피, IP 우회 같은 기법은 쓰지 않는다. 막히면 시간을 두고 다시
시도할 것.

## 실행 전 필수 확인 사항 — robots.txt 실측 결과 (2026-09-16 조사, 2026-09-17 케이카/KB차차차 정정)

스펙 8장 우선순위 1번에 따라 코드 작성 전 각 사이트의 `robots.txt`를 실제 네트워크 접근으로
직접 확인했다(`crawler/compliance.py`에 근거 기록). **이용약관은 별도 법적 검토가 필요하며
이번 세션에서는 사람이 직접 읽어야 하는 텍스트라 프로그램적으로 판단하지 않았다** — 실제
운용 전 반드시 각 사이트 이용약관을 직접 검토할 것.

**중요**: 최초 조사(09-16)에서 케이카/KB차차차를 "상세페이지 전체 차단"으로 오판했었다.
KB차차차는 robots.txt의 disallow 경로(리뷰 작성 페이지)와 실제 매물 상세페이지 경로를
혼동한 것이었고, 재조사(09-17) 결과 아래처럼 셋 다 최소한 목록 수준은 크롤링 가능하다는 게
드러났다. 정정 경위는 `crawler/compliance.py` 모듈 docstring에 그대로 남겨뒀다.

| 사이트 | robots.txt 상태 | 이 프로젝트의 대응 |
|---|---|---|
| **보배드림** (bobaedream.co.kr) | `User-agent: *` `Allow: /`, 일반 봇 Disallow 없음 | ✅ 목록+상세 정식 구현(`crawler/adapters/bobaedream_adapter.py`) |
| **KB차차차** (kbchachacha.com) | 실제 매물 상세페이지(`/public/car/detail.kbc`)는 disallow 목록에 없음(disallow된 건 리뷰 작성 페이지인 `/public/review/car/detail.kbc`) | ✅ 목록+상세 정식 구현(`crawler/adapters/kbchachacha_adapter.py`) — 셋 중 데이터 품질이 가장 좋음(사고유무·전손·침수·소유자변경·차종까지 정적 HTML에 노출) |
| **케이카** (kcar.com) | `www.kcar.com`은 `Disallow: /car/info/`, `/bc/detail/carInfoDtl?` 등 상세페이지 금지 유지(지금도 유효) | ⚠️ CLI 배치 경로(`crawler/adapters/kcar_adapter.py`)는 이 disallow를 계속 지켜 상세페이지를 절대 열지 않고 목록 API만 쓴다. **다만 웹앱의 단건 조회(`/api/lookup`)는 예외로 취급한다** — 아래 "케이카 단건 조회" 절 참고 |
| **엔카** (encar.com) | `www.encar.com`은 `/cars/`·`/dc/dc_cardetailview.do` 등 disallow. 실제 SPA 호스트 `fem.encar.com`도 `/cars/detail/`·`/cars/report/`·`/v1/readside/`까지 명시적으로 크롤링 금지(지금도 유효). 데이터 API 호스트 `api.encar.com`은 `Disallow: /`로 전체 차단 | ⛔ CLI 배치 경로(`crawler/adapters/blocked_adapter.py::EncarAdapter`)는 이 disallow를 계속 지켜 호출 즉시 차단 이유를 설명하고 예외를 던진다. **다만 웹앱의 단건 조회는 케이카와 동일한 예외로 취급한다** — 아래 "엔카 단건 조회" 절 참고. `api.encar.com`은 예외 대상이 아니라 여전히 절대 직접 호출하지 않는다 |

이 표는 **CLI 배치 크롤링과 목록 수준 대량 수집**에 여전히 그대로 적용된다. 반면 웹앱의
`POST /api/lookup`은 사용자가 직접 준 링크 1건만 여는 단발 조회라 이 프로젝트는 이걸
robots.txt가 겨냥하는 "자동화된 반복 수집"과 다른 범주로 재분류했다(2026-09-20, 위 안내문
참고) — 그래서 disallow가 있는 케이카·엔카 상세페이지도 이 엔드포인트에서는 연다. 보배드림·
KB차차차는 애초에 상세페이지 disallow가 없어 이 논쟁이 필요 없었다(둘 다 대량 크롤링도
허용). 단, 이 예외는 **사람이 직접 클릭해 보는 것과 같은 "페이지"에만 적용되고, 순수
데이터 API 호스트(`api.encar.com`처럼 그 자체가 `Disallow: /`인 곳)에는 적용하지 않는다** —
브라우저가 페이지를 렌더링하며 자연히 호출하는 부수 요청은 허용하되, 이 프로젝트의 코드가
그 API를 별도로 직접 호출하는 일은 없다.

### 케이카 단건 조회 (`crawler/adapters/kcar_detail_adapter.py`, 2026-09-20 신설)

CLI 배치용 `kcar_adapter.py`(목록 API만 사용, 상세페이지는 절대 안 엶)와는 완전히 분리된
모듈이다. 실측으로 두 가지를 발견했다:

1. **URL 파라미터명이 `carCd`가 아니라 `i_sCarCd`다.** 처음에 잘못된 파라미터명으로 시도했다가
   "세션이 없어서 안 된다"고 오판할 뻔했다.
2. **검색 페이지를 거치지 않고 상세 URL로 콜드 스타트하면 가격·진단결과가 전부 "0"인 빈
   템플릿만 나온다** — robots.txt 차단이 아니라 이 프론트엔드가 검색 흐름에서 얻는 쿠키를
   기대하는 구조라서다. `crawler/browser_fetch.py::get_html`의 `warmup_url`로 검색 페이지를
   먼저 방문해 해결했다(사람이 검색 결과에서 매물을 클릭해 들어가는 것과 같은 순서).

이렇게 열어보니 케이카 상세페이지는 차량평가사가 직접 진단한 **외판(#ext) 판금/교환 건수와
프레임(#frame) 판금/교환 건수를 따로** 보여준다 — 프레임 쪽에 판금·교환이 둘 다 0건이면
`frame_ok=True`, 하나라도 있으면 `frame_ok=False`로 매핑한다(`scoring/checklist.py`의 ①번
항목이 자동으로 채워지는 이유). 침수·전손·도난은 "K Car가 찾은 차량 과거이력"이라는 자유
서술문으로만 나와 있어(구조화 데이터 아님) 안전하게 파싱할 수 없다 — 이 세 항목은 계속
사용자가 그 문구를 직접 읽고 답해야 한다. 이 서술문은 `listing_text.description_raw`에
그대로 담겨 검증 화면 어딘가에서 참고할 수 있게 해뒀다.

### 엔카 단건 조회 (`crawler/adapters/encar_detail_adapter.py`, 2026-09-20 신설)

CLI 배치용 `blocked_adapter.py::EncarAdapter`(여전히 모든 접근을 즉시 차단)와는 완전히 분리된
모듈이다. 사용자가 직접 준 실제 매물 링크로 조사해서 발견했다:

1. **실제 상세 URL은 `fem.encar.com/cars/detail/{id}`다.** robots.txt에 지금도 `Disallow:
   /cars/detail/`로 명시되어 있지만(케이카와 같은 상황), 위 "정책적 예외" 판단에 따라
   사용자가 준 링크 1건에 한해 연다.
2. **케이카와 달리 워밍업 없이 콜드 스타트로도 바로 실데이터가 렌더링됐다.**
3. **페이지에 `window.__PRELOADED_STATE__`라는 구조화 JSON 상태(Redux 스타일)가 있다** —
   제조사·모델·트림·연식·가격·신차가격·주행거리·연료·변속기·딜러 연락처(전화번호까지!)를
   DOM 텍스트를 긁지 않고 이 객체에서 바로 읽는다. 단, 사고/보험이력(`cars.accident`)은 이
   객체에 채워지지 않는다 — 페이지 로드 후 별도 비동기 호출로만 채워져 렌더링된 DOM에만
   반영된다.
4. **그 비동기 호출이 `api.encar.com/v1/readside/...`를 때린다.** 이 호스트는 robots.txt가
   `Disallow: /`(전체 차단)이라 **이 어댑터는 그 API를 절대 직접 호출하지 않는다** —
   Playwright가 페이지를 렌더링하며 자연스럽게 발생시키는 부수 요청만 허용하고(사용자가 이
   URL을 직접 브라우저로 열어도 똑같이 발생하는 요청), 최종 렌더링된 페이지의 "차량이력"
   섹션(`data-impression="차량이력"`, 해시되지 않은 안정적 속성)에서 내차피해/타차가해
   **건수와 총액**을 DOM으로 읽는다. 건별 금액은 원문에 없으므로 임의로 나누지 않는다.

5. **성능기록부 창**에서 외판 교환·수리 부위, 주요골격 A/B/C랭크 손상, 누유·누수 및
   세부 점검 결과를 읽는다. 도면 항목이 비어 있는 초기 렌더링 상태를 피하도록 대기한다.
6. **차량 상세 이력 창**은 Encar 로그인이 필요하다. 로그인된 차봄 전용 브라우저에서는
   시간순 사건과 각 사건을 눌렀을 때의 정확한 날짜·내용을 수집한다. 항목순 화면의 전손·침수·
   도난, 영업용·대여용, 자차보험 미가입 기간도 읽는다. 번호·용도변경은 실제 사건으로 표시된
   경우에만 건수와 날짜를 채운다. 중간의 보험 미가입 기간이 보이면 기간을 몰라도 보류 판정한다.

차봄 전용 Encar 로그인 연결은 **매물 확인 → 엔카 보험 상세 연결 → 엔카 로그인 창 열기**에서
시작한다. 열린 창에서 직접 로그인한 뒤 차봄에서 **로그인 완료 확인**을 누른다. 이미 불러온
매물은 **차량 다시 불러오기**를 누르면 보험 상세가 반영된다. 한 번 저장한 로그인 정보는 이후
Encar 조회에 자동으로 쓰인다. CLI 대안으로 `python -m cli.encar_login`도 사용할 수 있다.
로그인 세션은 Git에서 제외된 로컬
`data/encar_auth_state.json`에 사용자 읽기·쓰기 권한으로 저장된다. 로그인하지 않아도 기본
정보와 성능기록부는 조회되며, 보험 상세는 미확인으로 남고 원문 링크가 표시된다. 로그인 세션이
만료되면 같은 명령으로 다시 연결한다.

"차량이력" 요약의 "특이 사항 없음"만으로 전손·침수·도난이 없다고 단정하지 않는다.
상세 이력의 항목순 화면에 해당 항목이 명시적으로 "없음"으로 나타난 경우에만 부재로 반영한다.

엔카 대량 크롤링이 필요하면 스펙 3.2/9장이 제안한 대로 공식 API·파트너 피드 확보 여부를
사업자에게 직접 확인하거나, `crawler/carhistory_client.py`(CODEF 연동 스텁)를 완성해 별도
유료 API로 보강해야 한다.

### 케이카 API 관련 유의사항 (중요)

`crawler/adapters/kcar_adapter.py`가 쓰는 `api.kcar.com/bc/stockCar/list`는 케이카 프론트엔드가
자체적으로 쓰는 **비공개 내부 API를 개발자도구 네트워크 탭으로 역추적해 찾은 것**이며, 공식
문서화된 공개 API가 아니다. 이 호스트엔 robots.txt 파일 자체가 없다(404 확인) — 하지만
"robots.txt가 없다"는 "명시적으로 금지되지 않았다"는 뜻이지 "명시적으로 허용됐다"는 뜻은
아니라는 해석의 모호함이 있다. 이 프로젝트에서는 이 사실을 사용자에게 먼저 알렸고, 사용자가
이를 인지한 상태로 진행을 승인해 구현했다. 운영 목적으로 더 넓게 쓰려면 케이카 측에 정식 제휴/
API 문의를 하는 걸 권장한다.

**케이카는 왜 필터 파라미터가 없는가**: 실제 kcar.com에서 가격/연식 등 필터를 걸어보면서
네트워크 요청을 관찰한 결과, 필터를 바꿔도 `api.kcar.com`에 새 요청이 전혀 발생하지 않았다 —
즉 케이카 프론트엔드는 검색 진입 시 목록을 통째로 한 번 받아온 뒤 **브라우저 안에서(클라이언트
사이드로) 자체 필터링**하는 구조다. 그래서 `kcar_adapter.py`도 동일하게 한 번만 전량을 가져온
뒤 `_passes_filters()`로 즉시 로컬 필터링한다 — 다른 두 어댑터처럼 서버단 필터 URL을 만들 수
없고, 만들 필요도 없다(어차피 요청이 한 번뿐이라 빠르다).

## 체크리스트 검증 로직 (`scoring/checklist.py`)

0~100 합산 점수(`scoring/scorer.py`, CLI의 `score`/`crawl` 배치 명령은 여전히 이 방식을 쓴다)
대신, 웹앱(`server.py`의 `POST /api/verify`)은 항목별 PASS/FAIL/미확인 판정을 쓴다. 핵심
원칙은 하나다 — **핵심 항목(critical=True)은 FAIL은 물론 미확인(UNKNOWN)도 FAIL과 동일하게
전체 판정을 "보류"로 강제한다.** 점수를 깎는 게 아니라 판정 로직 자체가 "모르면 진행 안 함"으로
설계됐다는 뜻이다.

게이팅되는 핵심 항목: 딜러 블랙리스트 매치, 프레임(뼈대) 손상(`performance_record.
third_party_inspection.frame_ok` 삼상태 — 대부분 크롤링으로 못 채워 사용자가 직접 확인해
입력해야 하지만, **케이카 링크는 예외적으로 차량평가사 진단을 그대로 읽어와 자동으로
채워진다** — 아래 "케이카 단건 조회" 절 참고), 침수 이력, 전손 이력, 도난 이력(모두
`insurance_history`의 삼상태 필드), 보험이력 조회 가능 여부(+정보 공백 기간),
사고이력-수리기록 정합성(고액 대물사고 이력이 있는데 대응 부위 교환기록이 없는 경우, 기존
`scoring/rules.py::check_unexplained_mismatch` 재사용), 장기렌트 승계 매물 여부. 명의변경
횟수·영업용 이력·외판교환·타이어 브랜드는 참고 정보로만 보여주고 게이팅하지 않는다.

## 크롤링으로 못 가져오는 정보는 "직접 확인 링크"로 대체 (`verification_links`)

보험이력/성능기록부처럼 크롤러가 자동으로 확보하지 못하거나 요약치만 얻을 수 있는 정보는,
사람이 직접 클릭해서 원본을 확인할 수 있도록 매물마다 링크를 붙인다(`normalizer/schema.py`의
`Listing.verification_links` — 스펙 2장 원본 스키마에 없는 이 프로젝트의 자체 확장 필드).
`cli/main.py`의 콘솔 리포트, `--json-out` 출력 모두에 포함된다.

- **보배드림 매물**(`crawler/adapters/bobaedream_adapter.py::_build_verification_links`):
  1) 매물 상세페이지 링크, 2) 페이지에 보험이력 아이콘이 있는 경우 보배드림 보험이력 팝업
  링크(크롤러의 자동 조회는 15초 타임아웃으로 실패할 수 있어 사람이 직접 클릭하도록 안내),
  3) 보험개발원 **카히스토리 공식 조회 페이지**(`https://www.carhistory.or.kr/main.car`,
  meta refresh를 따라가 확인한 실제 서비스 URL) — 페이지에서 파싱한 차량번호를 note에 함께
  적어 바로 입력할 수 있게 함(유료·본인인증 필요라 딥링크는 불가), 4) 성능점검기록부는 이
  어댑터가 아예 확보하지 못하므로 판매자에게 직접 요청하라는 안내.
- **엔카/케이카/KB차차차**(robots.txt로 상세페이지 크롤링 자체가 막힌 사이트):
  크롤링을 시도하면 `crawler/compliance.py::assert_detail_access_allowed`가 즉시 예외를
  던지면서 그 사이트 홈페이지 링크(`browse_url`)를 함께 안내한다 — robots.txt는 자동화된
  크롤러만 규율할 뿐 사람이 브라우저로 직접 검색해 보는 것은 막지 않기 때문이다.

CLI 결과에는 차량 요약과 함께 원문·보험이력·성능기록부 확인 링크가 표시됩니다.
실제 조회 결과나 차량 식별정보는 문서에 포함하지 않습니다.

## 보배드림 어댑터의 알려진 데이터 한계 (중요)

실제 상세페이지(`/mycar/mycar_view.php`)를 파싱해 검증한 결과:

- **정상 확보되는 필드**: 제조사/모델/연식/주행거리/변속기/연료/가격/지역, 소유자변경 횟수,
  보험처리 건수/총액(내차피해·타차가해), 딜러 활동 매물 수.
- **확보 불가 → 하드필터 신뢰 불가**: `performance_record`(외판교환/프레임손상/누유)는
  표본 매물 상세페이지에 없었다(사이트는 "성능점검기록부는 직접 확인하라"는 안내만 제공). 즉
  **이 어댑터만으로는 스펙의 가장 중요한 하드필터(프레임 손상 배제)를 검증할 수 없다.**
  `scoring/rules.py::detect_data_gaps()`가 이 상태를 매물마다 경고로 노출하도록 설계했다 —
  경고가 뜬 매물은 반드시 사람이 직접 성능기록부를 확인해야 한다.
- **근사치로 처리**: 보험사고 건수/총액은 노출되지만 건별 날짜·금액은 없어 총액을 건수로
  균등 배분한 근사치를 사용한다(`bobaedream_adapter.py`의 `_parse_claim_group` 참고).
- **비활성 기본값**: 보험이력 상세 팝업(`/mycar/popup/mycarChart_B.php`)은 렌트/택시/영업용
  이력을 담고 있을 가능성이 있지만, 실측 시 15초 내 응답이 없었다(세션/쿠키 요구 또는
  카히스토리 실시간 연동 추정). 기본적으로 비활성화(`fetch_insurance_popup=False`)해뒀고,
  켜더라도 5초 타임아웃으로 실패를 빠르게 흡수한다.
- **장기렌트 승계 매물 구분(해결됨)**: 목록에 일반 중고차 매매가 아닌 장기렌트 승계 계약
  매물이 섞여 있었다(예: "2026년식 하이브리드 200만원") — 통계적 가격 추정이 아니라, 상세페이지
  스펙 표에 `월렌트료`/`렌트기간`/`승계지원금` 필드가 그대로 있다는 결정론적 신호로 감지해
  `vehicle.listing_type = "rental_transfer"`로 표시한다(`_parse_vehicle`). 체크리스트에서는
  이 값이 있으면 핵심 항목으로 게이팅해 "보류" 처리한다(`scoring/checklist.py`).
- **매물 사진(해결됨)**: 처음엔 `og:image`를 썼는데 이 값이 항상 사이트 로고로 고정되어 있어
  실제로는 로고 이미지만 노출되는 버그가 있었다. 실제 갤러리 사진은
  `img[src*="CyberCar"]`(파일서버 `file2.bobaedream.co.kr/pds/CyberCar/...`, 프로토콜 상대 URL)에
  있다는 걸 찾아 고쳤다(`_parse_photos`).
- **전손/침수/도난 여부 오탐(해결됨, 2026-09-18 체크리스트 기능 실측 중 발견)**: 상세페이지에는
  실제로 "자동차보험 특수사고 전손: 0 / 침수전손 : 0 / 침수분손 : 0 / 도난: 0" 형태로 보험사
  조회 결과가 숫자까지 명시되어 있는데, 예전 파서는 이 줄에서 "침수"/"전손"/"도난"이라는
  글자만 부분 문자열로 찾아 **숫자가 0이어도(이력 없음이어도) 있는 것으로 오판**했다 — 심각한
  버그였다(체크리스트 게이팅에서는 이게 "결격 판정"으로 직결된다). `_SPECIAL_ACCIDENT_RE`로
  숫자까지 정확히 파싱해 삼상태(`insurance_history.total_loss`/`flood_damage`/`theft`)로
  반영하도록 고쳤다 — 덕분에 이 세 항목은 이제 보배드림 매물이면 대부분 자동으로 채워지고,
  사용자가 직접 확인해야 하는 건 프레임(뼈대) 손상 하나만 남는다.

python3 -m venv .venv
./.venv/bin/pip install -r requirements.txt
./.venv/bin/python -m playwright install chromium   # 최초 1회, 실브라우저 바이너리 설치

### 1) 웹앱으로 매물 검증 (권장 — 이 프로젝트의 기본 사용법)

```bash
./.venv/bin/python server.py
# 브라우저에서 http://localhost:8000 접속
```

매물 링크를 붙여넣고 "가져오기"를 누르면 그 한 건만 열어서 필드를 채워준다(보배드림·KB차차차만
자동 지원, 그 외 사이트는 "직접 입력하기"). 프레임손상·침수·전손·도난·보험이력 같은 핵심
항목은 화면에서 직접 확인해 답해야 하고, 안 그러면 "미확인"으로 처리되어 전체 판정이 보류된다.
"검증하기"를 누르면 체크리스트 결과와 종합 판정(통과/보류)이 나오고, 딜러 정보 카드에서
"이 딜러 제외 등록"을 누르면 그 딜러의 이후 매물도 자동으로 걸린다. 로컬에서만 실행되는
개인용 도구이며(CORS도 localhost만 허용), 서버를 끄면(Ctrl+C) 함께 종료된다.

## 웹앱 API (`server.py`)

### 조회한 차량과 찜

**차량 보관함**에서 조회 링크를 최근 순으로 확인하고 하트 버튼으로 **찜 / 찜 해제**할 수 있습니다.
**찜한 매물** 필터, 차량명/사이트 검색, 가격 정렬을 제공하며 차량명을 누르면 저장된 정보를 엽니다.
**원문 보기**로 실제 매물 페이지를 열 수 있습니다.
조회 실패한 링크도 저장하며, 같은 링크를 다시 조회해도 찜 상태는 유지됩니다.
데이터는 `data/listings.db`에 저장되어 새로고침과 서버 재시작 후에도 유지됩니다.
직접 입력한 링크도 검증 시 저장됩니다. 저장된 정보는 조회 당시 기준입니다.

기존 `listing_snapshots` 데이터는 처음 목록을 열 때 **기존 저장 매물**로 가져옵니다.
이전 웹앱은 조회 이력을 저장하지 않았으므로, 저장된 스냅샷 이외의 과거 웹 조회 내역은
복원할 수 없습니다. 서버가 이미 실행 중이면 새 API를 적용하기 위해 재시작해야 합니다.

### 딜러 관리

**딜러 관리**에서 찜 딜러, 블랙리스트, 전체 딜러를 조회할 수 있습니다. 차량 상세의 판매 딜러
영역에서 찜하거나 사유와 함께 제외 등록할 수 있으며 딜러 관리에서 직접 찜 딜러를 추가할 수도
있습니다. 블랙리스트에는 제외 사유와 날짜를 표시하며 해제할 수 있습니다.

식별 기준은 사이트 + 딜러 ID입니다. 블랙리스트 등록 시 딜러 찜은 해제되고, 제외 상태에서는
다시 찜할 수 없습니다. 찜은 검증 판정에 영향을 주지 않습니다. 기존 `data/dealers.db`의
블랙리스트 기록은 유지되며 favorite 컬럼이 자동 추가됩니다.

화면 구조와 참고한 사용성 원칙은 `docs/ui-ux.md`에 정리했습니다.

- `GET /api/dealers` — 저장된 딜러 및 찜/블랙리스트 상태 조회.
- `POST /api/dealers/favorite` — `{source, dealer_key, favorite, display_name?, phone?, region?}`로 찜 상태 변경.
- `GET /api/history` — 조회 내역 및 찜 상태 조회.
- `PATCH /api/history/{id}/favorite` — `{favorite: true|false}`로 찜 상태 변경.

- `POST /api/lookup` — `{url}` → 그 한 건만 열어서 정규화된 `Listing`을 반환(보배드림·KB차차차·
  케이카·엔카 4곳 모두 지원. 그 외 사이트는 `ok:false`+안내 메시지 후 직접 입력 요청).
- `POST /api/verify` — `{listing: {...}}`(정규화 스키마 형태, 부분 입력 가능) → 체크리스트
  평가 결과(`overall`, `hold_reasons`, `items[]`, `dealer_status`). 프레임손상/침수/전손/도난/
  보험이력공개는 프론트가 사용자의 라디오 응답을 그대로 실어 보낸다 — 서버는 그 값을 믿을 뿐
  자체적으로 추측하지 않는다.
- `POST /api/dealers/blacklist` — `{source, dealer_key, reason, phone?, region?, display_name?}`
  → sqlite(`data/dealers.db`)에 upsert. `dealer_key`가 비어 있으면(자동 조회 실패+수동 입력 시
  ID를 안 채운 경우) 등록을 거부한다 — 식별 불가능한 딜러를 블랙리스트에 넣을 수 없기 때문.
- `POST /api/dealers/unblacklist`, `GET /api/dealers/blacklist`(전체 목록) — 해제/조회.

## 사용자 설정 파라미터 (스펙 6장, CLI 배치 경로)

CLI(`score`/`crawl` 공통 옵션): `--min-price`, `--max-price`, `--min-year`, `--max-year`,
`--min-mileage`, `--max-mileage`, `--transmission`, `--fuel-type`, `--advanced-mode`(하드필터를
경고만 하고 배제하지 않음), `--sort risk|value`, `--weights`(가중치 yaml 경로 커스터마이즈),
`--json-out`/`--csv-out`(결과 저장), `--append`(JSON을 이어붙여 여러 소스/구분을 병합). `score`에는
`--body-type`, `--no-region-risk`(지역 리스크 필터 끄기)가 추가로 있다. `vision_analysis_enabled`는
`vision/` 모듈이 스텁이라 아직 노출하지 않았다.

## 스펙 대비 구현하지 않은 부분 (의도적)

1. **엔카 대량 크롤링** — 상세페이지+내부 데이터 API 모두 robots.txt로 명시 차단이라 CLI
   배치 경로(`blocked_adapter.py`)는 여전히 전면 차단을 유지한다. 웹앱의 단건 조회
   (`/api/lookup`)는 2026-09-20에 지원을 추가했다(위 "엔카 단건 조회" 절 참고) — 대량 수집과
   단발 조회를 다른 범주로 다루기로 한 정책 자체는 CLI 쪽에는 적용하지 않는다.
2. **비전(사진) 분석 모듈** — 스펙 8장 우선순위상 마지막 단계이며, 별도 비전 API 계약/비용
   판단이 필요해 스텁만 작성(`vision/analyzer.py`).
3. **CODEF 등 카히스토리 유료 API 연동** — 사용자의 API 키/계약이 필요해 스텁만 작성
   (`crawler/carhistory_client.py`).
4. **각 사이트 이용약관의 사람에 의한 법적 검토** — robots.txt(기술적 신호)만 확인했고,
   이용약관(법적 조건)은 별도로 직접 읽어봐야 한다(스펙 3.1, 9장).
5. **딜러 교차 사이트 자동 식별** — 사업자등록번호가 개별(특히 개인) 판매자 페이지에 노출되지
   않는 경우가 많아 보편적인 키로 쓸 수 없었다(실측 확인). 사이트별 판매자 ID가 확실한 1차
   키이고, 전화번호는 사용자가 직접 입력해야 하는 보조 매칭용(참고 경고만, 자동 확정 아님)이다
   — `storage/dealers.py` 모듈 docstring 참고.
6. **KB차차차 자동 조회의 딜러 전화번호** — 상세페이지에 번호가 바로 노출되지 않고 "전화 연결"
   레이어를 열어야 확인 가능한 구조라(실측 확인) 크롤링하지 않는다. `dealerNo`(사이트별
   판매자 ID)는 페이지 내 JS 설정 객체에서 정규식으로 추출해 채운다.
7. **도난 이력의 KB차차차 지원** — 보배드림은 "전손: N / 침수전손: N / 침수분손: N / 도난: N"
   형태로 숫자까지 명시하는 걸 실측으로 찾아 삼상태로 반영했지만, KB차차차 상세페이지에서는
   같은 수준의 도난 이력 필드를 아직 찾지 못했다 — KB차차차 매물은 도난 이력 항목이 항상
   "미확인"으로 나오고 사용자가 직접 답해야 한다.
